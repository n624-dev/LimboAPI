# Minecraft 26.3 fork

This fork starts at upstream commit `bfef5799f21d73a80155035c3430f6654aa6b9f8`.
That commit already implements protocol 777 support. The fork focuses on reliable
builds, regression tests, and verifying the runtime with Velocity and downstream plugins.

## Development and verification

Build on the development machine with JDK 25, using a shell-local `JAVA_HOME`:

```sh
export JAVA_HOME=/path/to/jdk-25
export PATH="$JAVA_HOME/bin:$PATH"
./gradlew -p buildSrc --no-daemon -Dorg.gradle.jvmargs=-Xmx512m test
./gradlew --no-daemon --max-workers=2 -Dorg.gradle.jvmargs=-Xmx4g build
```

The initial build downloads vanilla server JARs and generates mappings for supported
Minecraft versions. Allow time, network access and disk space for this step. Generated
Minecraft files are build inputs and caches; they are not committed to this repository.

Run the resulting plugin in a separate Debian 13 VM with Java 25. Transfer the host-built
JAR and verify its SHA-256 before testing. Restore a clean guest snapshot when necessary.
Keep validation credentials and worlds separate from production.
Stop the game processes and power off the validation VM at the end of each session.
Leave VM autostart disabled; start it explicitly for the next validation session.

The mapping build needs a 4 GiB Gradle heap in this environment; a 2 GiB trial showed
heap pressure during block-state mapping generation. Each Minecraft generator process
is limited to 1 GiB and ten minutes. Its merged output goes to a per-version
`generator.log`; nonzero exit codes, timeouts and missing reports fail the build.

Initial runtime targets:

| Component | Version/build |
| --- | --- |
| Java | Eclipse Temurin 25.0.4.1+1 |
| Velocity | 4.2.0 build 30 |
| Paper | 26.3 build 190 |
| Geyser-Velocity | 2.12.0 build 1256 |
| Floodgate-Velocity | 2.2.5 build 141 |

These are validation targets, not a declaration that every component is a stable release.
Automated startup and protocol probes do not substitute for an authenticated vanilla Java
client or a Bedrock client. Record passed, failed and unperformed checks separately.

## Acceptance sequence

1. Build and static checks, including a clean mapping generation.
2. Velocity startup and Limbo creation with a small validation plugin.
3. Java 26.3 login, chunks, teleport acknowledgement, waiting and reconnect.
4. Transfer to Paper, return to Limbo and repeat the transfer.
5. Geyser/Floodgate initialization and actual Bedrock login.
6. Controller API compatibility, waiting/ready transitions, whitelist rejection and failures.

Use independent fork versions and publish source revisions, checksums and limitations with
artifacts. CI uploads build artifacts for review; it does not publish to upstream Modrinth
or replace upstream development releases. Preserve the upstream plugin/API license files.
